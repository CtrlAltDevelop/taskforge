# 02 — Roadmap

One feature per phase. Do them in order; each lists its dependencies.
Groups are just for reading — a phase is still exactly one feature.

## Status

- **Phase 00** — implemented on `develop`; verified on web (real browser) and native Dart. Not yet verified: Android, iOS, Windows, Linux runs, CI on GitHub, fresh-clone boot.
- **Phase 01** — implemented on `develop`: backend policy + refresh grace window + Postgres, Flutter sign-in/up, sessions, gRPC `Me`. Passwords are hashed with Argon2 (PBKDF2 hashes upgrade on login). Verified: backend suite (SQLite and Postgres), Flutter tests, a live end-to-end run, and the web UI in a real browser. Not yet verified: CI on GitHub (incl. the new Postgres job), the new UI on macOS/Android/iOS.
- **Phase 02** — implemented on `develop`: workspaces backend (`WorkspaceController`, logo upload, scoping helpers, `purge_workspaces`) and Flutter onboarding/switcher/settings. Create, switch, invite and role flows run in a real browser against real Envoy. Not run on a device. WS non-member close deferred to phase 16 (the socket helper exists).
- **Phase 03** — implemented on `develop`: members and invitations backend (`MemberController`, `InvitationController`, REST invite preview/accept) and Flutter Members screen, invite dialog and `/invite/:token` deep link. Invite emails go out from a post-commit signal on an in-process worker (durable job queue comes with a later phase). Deep link checked in a real browser (web) and on macOS; not run on Android, iOS, Windows or Linux. Not done: Windows/Linux scheme registration, HTTPS app links; web `/invite/*` SPA fallback is for phase 38.
- **Phase 04** — implemented on `develop`: permission registry, `can()`/`require()` on every workspace-scoped endpoint, custom roles (`RoleController`, `PermissionController`, `MemberController.SetRole`), deny reasons on gRPC and REST, and the Flutter Roles matrix, role picker and `PermissionGate`. Invitations can carry a role. Checked in a real browser against real Envoy (denial reason headers readable on web, role edit conflict). Not run on a device. The socket error-frame helper exists; the realtime channel itself arrives in phase 16.
- **Phase 05** — implemented on `develop`: projects backend (`ProjectController`, keys locked once tasks exist, open/private visibility through the single `visible_to` query path, archive/restore, favorites, feature toggles, safe task counter `number_task`, a project creator can manage their own project) and Flutter project sidebar, create dialog, settings with members, archived list and admin private list. Backend suite on SQLite and Postgres, Flutter tests; not run in a real browser or on a device. Phase 06 must number tasks via `number_task` and read only through `visible_to`.
- **Phase 06** — implemented on `develop`: tasks backend (`TaskController`: create/get/update/delete/restore and a server-streamed, cursor-paged `List`; display ids `KEY-N` from the project counter; field-level optimistic locking so different fields merge and the same field answers `ABORTED` with the current value; soft delete plus a trash list; fractional-index positions; `task.*` permissions) and Flutter quick-add, streamed list with skeleton/empty/error states, detail side panel or page, assignee chips (project members only), date pickers, priority icons, conflict dialog, optimistic edits with rollback, a Trash screen with Restore, and a marked-up-text description editor that round-trips the shared rich-text document. Full backend suite (SQLite; tasks and projects also on Postgres: 50 parallel creates, 10,000-task first page) and Flutter tests pass; not run in a real browser or on a device (Docker stopped responding when I tried). The description is a text box, not a WYSIWYG editor; that can come with Docs.
- Toolchain: the app needs Flutter 3.47.9 (Dart 3.13.7+); older SDKs fail `flutter pub get`. On Windows, `make` assumes macOS paths, so run the proto and test steps by hand.
- **Phase 07** — implemented on `develop`: per-project workflows (`WorkflowController` Get/Update/Validate, `TaskController.Move`): statuses with name, colour, category and order, one default, optional restricted transitions with role and assignee conditions, atomic whole-workflow save that rejects an invalid graph with the full list of problems (a conflicting save is merged with the other person's changes and every decision is shown before anything is saved), an optional per-project *Restrict creation* rule (new tasks start in the default status only; off by default), deleting a status moves its tasks in the same transaction, `TRANSITION_NOT_ALLOWED` with the reason; `Task.status` is now a project status (migration converts every existing task). Flutter: Project settings → Workflow editor (touch drag-to-reorder, category/colour/default, per-status move chips with conditions, delete-with-migration dialog, validation panel, node-and-arrow picture on wide screens) and a status picker that offers only allowed targets. Not run in a real browser or on a device; the *all subtasks done* condition waits for phase 08.
- **Phase 08** — implemented on `develop`: subtasks to any depth (parent link, materialized path and tree key, cycle and depth checks, subtree re-parent in one query, progress that rolls up in the same transaction, delete as `subtree` or `promote`, restore of a deleted batch, tree-order paging with `include_subtasks`, `Move` that takes open subtasks along, and the workflow condition "all subtasks done" in the editor). Flutter: indented tree with chevrons, progress rings, inline add, "Move under…", press-and-drag to nest on wide screens, breadcrumb and subtask checklist in the detail, delete-mode and complete-all prompts. 5,000-task tree tested on the server and in the app. The tasks, workflows and projects suites (including the race and migration tests) pass on PostgreSQL; not run in a real browser or on a device.
- **Phase 09** — implemented on `develop`: typed task links (`LinkController`: blocks / blocked by, relates, duplicates), seen from both ends, with loop protection that names the path, a blocked lock and a completion guard that a project manager can override (recorded). Hidden far ends show as "Restricted task". Blocked tasks name their blockers, the picker searches every project you can open, link changes are announced for phase 16, and the loop race is tested in parallel on PostgreSQL. Not done: a board badge (phase 12). Not run in a real browser or on a device.
- **Phase 10** — implemented on `develop`: per-project custom fields of nine types (`FieldController`; archive and restore within 30 days, option remap, required and default values, per-field edit conflicts, index-backed value filters) and Flutter Fields settings, `FieldInput`, task detail section and a required-values dialog on quick-add. Backend suites on SQLite and PostgreSQL (index plans, parallel edit race) and Flutter tests pass; not run in a real browser or on a device. Real list columns wait for phase 11, board group-by for 12, filtering UI for 14.
- **Phase 11** — implemented on `develop`: the list is a virtualized table (sort, group with server counts, resize, show/hide columns, inline edit, keyboard operation, phone cards) over `Tasks.List` with `sort`/`group_by`, a streaming `BulkUpdate` with per-task results, and personal/shared layouts in the new `savedviews` app. Backend and Flutter suites pass on SQLite; PostgreSQL, device frame rate and a real browser were not checked.
- **Phase 12** — implemented on `develop`: the Kanban board (`BoardController` `Get`/`ListColumn`/`Move`; columns by status, priority, assignee or a select field; lazy columns of 30 cards; fractional ranks changed one card at a time with server-side respacing; drag, Move-to menu, WIP limits, swimlanes, card fields, per-column quick-add) and a List | Board switch in the app. Backend and Flutter suites pass on SQLite; PostgreSQL, device frame rate and a real browser were not checked.
- **Phase 13** — implemented on `develop`: the calendar (`CalendarController` `ListRange`/`ListUnscheduled`; date-only tasks by their start–due days; month, week and day, phone agenda; drag to move, drag an edge to resize, unscheduled tray, colour by status or priority, week-start choice; personal `calendar` layouts) and a List | Board | Calendar switch. Backend and Flutter suites pass on SQLite; the optional due time and the link-aware warning are built; PostgreSQL and a real browser/device were not run.
- **Phase 13b** — implemented on `develop`: the workspace calendar (`ListWorkspaceRange` across every visible, non-archived project; `/calendar` from the home screen; colour by project with a hide/show legend, or by status/priority; drag, resize, link warnings and due times as in phase 13; no tray). Backend and Flutter suites pass on SQLite; PostgreSQL and a real browser/device were not run.
- **Phase 14** — implemented on `develop`: TFQL and saved filters (hand-written parser with positions, id-based AST that renders back to text, ORM compiler, `QueryController` Validate/Suggest, `FilterController` List/Save/Delete, `filter_ast` on list, group counts, board and calendar; a filter bar with a visual builder and a highlighted text editor in the app). Backend and Flutter suites pass on SQLite; PostgreSQL (the statement timeout) and a real browser/device were not run.
- **Phase 15** — implemented on `develop`: the timeline (`TimelineController` `Get` / `CriticalPath` / `PreviewShift` / `ApplyShift` / working days; a pure scheduling engine with cascade through blocking links and a critical path; a per-workspace working-day calendar; a canvas chart with drag, resize, zoom, arrows, today line, grouping, PNG export, a list fallback; personal `timeline` layouts) and a List | Board | Calendar | Timeline switch. Backend and Flutter suites pass on SQLite; PostgreSQL, device frame rate and a real browser were not run.
- **Phase 16** — implemented on `develop`: realtime sync (`/ws/sync` socket with rooms checked on join and on delivery, a change log with cursor catch-up through `SyncController`, access-change events that drop rooms at once, presence with an editing hint, a reconnecting client state machine, live indicator, banner and row flash). Backend and Flutter suites pass on SQLite; a real network, a browser and PostgreSQL were not run.
- **Phase 17** — implemented on `develop`: comments and mentions (`CommentController`, safe rich-text bodies, one level of replies, edit history, reactions, pinning, comment to subtask, a permission-aware `@` picker with an optional grant for private projects, `user.mentioned` once per person per version, live `comment.*` events; in the app a composer with toolbar, optimistic send with retry, replies, reactions and history inside the task). Backend and Flutter suites pass on SQLite; PostgreSQL, a real browser and a real network were not run.
- **Phase 18** — implemented on `develop`: attachments (chunked, resumable uploads over REST, content sniffing that refuses programs, optional ClamAV, isolated thumbnails for images and PDF, short-lived signed links with Range, per-workspace dedupe and quota, `AttachmentController` List/Delete/Usage, `attachment.*` events; in the app a drop zone, picker, camera/gallery, paste, progress with cancel/retry/resume, a thumbnail grid, a viewer and attachments on comments). A real 1 GiB upload resumed after a server restart; backend and Flutter suites pass on SQLite; PostgreSQL, a real browser and a device were not run.
- **Phase 19** — implemented on `develop`: notifications (new `inbox` app: `Notification`, per-event preferences, quiet hours, digests, watchers, push devices and a `Delivery` log; de-duplicated and folded bursts, actor and lost-access filtering; `InboxController`/`WatcherController`/`PrefController`/`DeviceController`; FCM push and email with a signed unsubscribe link; `make tick` as the clock; in the app an inbox with filters, optimistic read, snooze and archive, a preference matrix, a watch button and a live sidebar and app-icon badge). Backend and Flutter suites pass on SQLite; app-side push tokens (Firebase project files are not in the repo) are not built, and a real device, browser and PostgreSQL were not run.
- **Phase 20** — implemented on `develop`: global search (`SearchController` Query/Remember/Recent; a folded-text index of tasks and comments kept current by signals, permission filtering inside the SQL, operators `in:` `assignee:` `status:`, id jump, highlights, recent searches, per-person rate limit; PostgreSQL full-text + trigram typo tolerance; in the app a search box on `/` or Ctrl/Cmd+K with grouped results, keyboard navigation and filter chips). Backend and Flutter suites pass on SQLite; the PostgreSQL path, typo tolerance and the 200k-task p95 target were not run (no PostgreSQL here).
- **Phase 21** — implemented on `develop`: time tracking (`TimeController`; a server-side timer with one running entry per person enforced by the database, manual entries with overlap and over-24 h flags, `time.log` / `time.edit_others`, task estimates, weekly timesheets clipped to local days, per-person project totals, a `timer.changed` live event, an inbox reminder for a forgotten timer; in the app a timer chip, a Time section in the task, a Timesheet screen and a mobile ongoing notification). Backend and Flutter suites pass on SQLite; the desktop tray indicator is not built, and PostgreSQL, a real device and a real browser were not run.
- **Phase 22** — implemented on `develop`: sprints (new `sprints` app: planned/active/completed state machine with one active sprint per project, backlog, planning moves, points, carry-over to next sprint or backlog, burndown with ideal line and scope-change steps, velocity of the last 6, midnight snapshots via `make tick` with back-fill, `currentSprint()` in TFQL, `sprint.manage`; a stored sprint capacity in points and hours; in the app a two-pane planning screen, capacity bar (falls back to the average velocity), start/complete dialogs, burndown (back-filled days ringed) and velocity charts on shared chart helpers, and the board's "Current sprint" filter with a link from the sprint screen). Backend and Flutter suites pass on SQLite and the backend suite on PostgreSQL; a real browser/device was not run. The baseline counts only the tasks that are open at the start (tasks already Done are left out).
- **Phase 23** — implemented on `develop`: docs (new `docs` app, label `wikidocs`: nested pages, versioned validated blocks that keep unknown ones, throttled revisions with restore, per-page restriction, `[[` mentions and task cards that obey the viewer, backlinks, Markdown export, search and live events, "editing now" presence; in the app an in-house block editor with slash menu, autosave, conflict merge dialog, revision drawer, restrict dialog and a Related docs panel on tasks). Backend and Flutter suites pass on SQLite and the backend suite on PostgreSQL; Redis presence and a real browser/device were not run. Limits: no selection across blocks, a pasted task key (not link or id) is not recognised, the slash menu does not flip above near the screen bottom.
- **Phase 24** — implemented on `develop`: automations (new `automations` app: six triggers, seven actions, TFQL conditions, dry run, run history with a "why didn't this run" explanation, loop guard at depth 5, per-rule rate guard, idempotency per event, owner permission ceiling at run time, auto-disable when a used status/field/person is gone, SSRF-safe webhooks with a total deadline; no Celery, so an in-process bounded queue plus `make tick` for due dates; in the app a When/If/Then builder, dry-run dialog and run history). Backend and Flutter suites pass on SQLite and the backend suite on PostgreSQL (which found and fixed a row-lock bug); the real thread pool, webhook TLS and a real browser/device were not run. The live `automation.run` hint carries the run id only (the sync event has no status slot).
- **Phase 25** — implemented on `develop`: command palette and shortcuts (new `shortcuts` app: a person's own key bindings, `ShortcutController` Get/Set, chord validation, conflict refusal; in the app an action registry with a generated cheat sheet, `Ctrl/Cmd+K` palette with `>` `#` `@` modes and search, rebinding dialog, phone quick-actions sheet). Task-level actions (new task, status, assign to me, start/stop timer) are registered, and a rebinding is picked up live on other devices (`shortcuts.changed`). Backend suite on SQLite and the Flutter suite pass; not run in a real browser or on a device.
- **Phase 27** — implemented on `develop` (ahead of 26, whose cycle time needs its history): audit log (new `audit` app: append-only `AuditEntry` written in the change's transaction, signal receivers for 24 models plus explicit recording where the ORM's signals are skipped, redaction, batch ids, sign-in events, `audit.view`, gRPC `Audit.List/Export` and `Activity.ForTask`; in the app an Activity section in task detail and an admin Audit log screen with filters, before/after and CSV export). Backend suite on SQLite and the Flutter suite pass; the PostgreSQL trigger and the 1M-row timing were not run (no database here).
- **Phase 26** — implemented on `develop`: dashboards (new `dashboards` app: personal, project or workspace dashboards of seven widget types over TFQL filters, five measures including cycle time from the audit history, per-viewer numbers with a viewer-keyed 60 s cache, drill-down that lists exactly what a bar counted, templates, CSV export, `dashboard.manage`; in the app a draggable and resizable grid, a widget editor with live preview and one shared chart module). Backend suite on SQLite and the Flutter suite pass; the PostgreSQL timeout path and timing were not run.
- **Phase 28** — implemented on `develop`: recurring tasks (new `recurrence` app: RRULE rules in two modes, a row-locked clock `recurrence_tick` in `make tick` with a catch-up cap, after-completion hook, edit this/future, pause/stop with auto-pause reasons, ghost dates for the calendar; in the app a Repeat chip, editor with live preview, stop-or-keep prompt on deleting a template and calendar ghosts). Backend suite on SQLite and the Flutter suite pass; PostgreSQL and a real device were not run.
- **Phase 29** — implemented on `develop`: import and export (new `imports` app: streaming parsers for Jira CSV/JSON, ClickUp CSV/JSON, any CSV and TaskForge's own export; mapping proposed from the file, dry run, chunked idempotent resumable import with level-by-level parents, links, sprints, comments and placeholders for people who are not members yet, undo of exactly what a job made, project and workspace export as a zip with a signed link; `data.manage`; in the app a five-step wizard, history with undo, and an export dialog). Backend suite on SQLite and the Flutter suite pass, including a 50,000-issue Jira import and an export-to-import round trip; PostgreSQL and a real browser or device were not run.
- **Phase 30** — implemented on `develop`: offline mode (server idempotency by `client_mutation_id`; in the app a Drift copy of what was read, an outbox of changes made offline that is folded, ordered and sent when back, conflict and refusal items with keep mine / take theirs / merge, offline task, comment and attachment creation, offline banner, pending marks, storage settings with cache cap and kept projects, wipe at sign-out). Backend suite on SQLite and the Flutter suite pass; the browser stays online-only, and a real device and PostgreSQL were not run.
- **Next:** phase 31.
- Phases 26–40 — planned.
