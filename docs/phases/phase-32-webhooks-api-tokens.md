# Phase 32 — Webhooks and API Tokens

**Status:** DONE

## Feature
A **public REST API** secured by personal/service **API tokens**, plus outgoing **webhooks** for events.

## Why it exists
Integrations are how teams connect CI, chat and scripts. Incumbents rate-limit or paywall API/webhook use. Ours is open, documented (OpenAPI generated by Django Ninja), and observable.

## How it works (plain words)
A user (or admin for service accounts) creates a **token** with a name, scopes (`tasks:read`, `tasks:write`, …) and optional expiry; the secret is shown **once**, stored only as a hash. The public API is the Ninja REST surface under `/api/v1/` using `Authorization: Bearer tf_…`; docs at `/api/docs`. A **webhook** subscribes a URL to events (`task.created`, `task.status_changed`, `comment.created`…). On each event the server sends a signed POST (HMAC-SHA256 header with timestamp) via Celery, retrying with backoff; each delivery attempt is logged and can be replayed from the UI.

## Scope
**In:** token CRUD/revoke/last-used, scopes, rate limiting per token, public v1 endpoints for core objects (workspaces, projects, tasks, comments), webhook CRUD, event catalog, signing, retries, delivery log + redeliver, test ping, audit entries for token creation and revocation (`token.created`, `token.revoked`, via `audit.recorder`; owed by phase 27).
**Out:** OAuth app marketplace, GraphQL, inbound “apps” platform.

## Data model
- `ApiToken(id, workspace, owner, name, prefix, hash, scopes[], expires_at, last_used_at, revoked_at)`
- `Webhook(id, workspace, project nullable, url, secret, events[], active)`
- `WebhookDelivery(id, webhook, event, payload, status_code, response_snippet, attempt, next_retry_at, at)`

## API surface
- REST (public v1): resources above; `GET/POST /api/tokens`, `/api/webhooks`, `/api/webhooks/{id}/deliveries`, `POST …/redeliver`
- Tokens also accepted on gRPC metadata (service-to-service use).

## Flutter UI
Settings → Developer: token list/create (copy-once secret dialog), scopes picker, webhook editor with event checklist, delivery log with request/response viewer and “Resend”.

## Rules and edge cases
- **SSRF protection:** resolve target host and block private/loopback/link-local ranges (configurable allowlist for self-hosters); no redirects followed.
- Timeouts 10 s; max payload size; exponential backoff up to 24 h then disable with notice.
- Tokens inherit owner’s permissions **intersected** with scopes.
- Idempotent event ids so receivers can dedupe.

## Acceptance criteria
- [x] Create task via curl with a token; scope violation → 403
- [x] Webhook receives correctly signed event; tampered signature fails verification sample
- [x] SSRF attempts to `127.0.0.1`/metadata IP are refused
- [x] Redelivery works from UI
- [x] Creating and revoking a token each leave an audit entry (actor, token name and prefix; never the token or its hash)

## Tests
Hash/prefix lookup, scope enforcement, signature fixtures, SSRF suite, retry schedule.

## Depends on
Phases 01, 04, 06; event catalog shared with 16/24/27.

## Implementation notes
Accepted deviations from the plan above:
- Tokens are personal only; there are no service-account tokens (the plan's "or admin for service accounts" is not built).
- A token can never manage tokens or webhooks (a leaked token cannot mint a longer-lived one).
- A webhook switched off after 24 hours of failures shows `disabled_reason` and a `webhook.disabled` audit entry, not an inbox notice.
- The public task schema omits the description.
